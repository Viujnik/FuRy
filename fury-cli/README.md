# FuRy-cli workspace

## За что отвечает

`fury-cli` - исполняемый крейт workspace: в `Cargo.toml` объявлен
`[[bin]] name = "fury"`, поэтому после сборки получается команда `fury`, а не
библиотека. Назначение у неё оффлайновое: кодогенерация кросс-языковых моделей
из схем реестра. CLI не сериализует данные в рантайме и не ходит в базу - он
читает схемы (из файла реестра или через импорт Python-модуля) и печатает
TypeScript-классы, а рядом кладёт бинарный блоб реестра, чтобы фронтенд мог
скормить его `loadRegistry` (см. README fury-ts).

В workspace крейт входит в `default-members = ["fury-core", "fury-cli"]`,
поэтому обычный `cargo build` из корня собирает именно ядро и CLI: fury-py
требует maturin, fury-ts - wasm-pack, и в дефолтную сборку они не лезут.

---

## Точка входа - src/main.rs

Файл крошечный и делает три вещи. Объявляет модули; реэкспортирует
`pub use fury_core::schema::registry::get_global_registry` на уровень крейта -
чтобы `commands/generate.rs` писал `crate::get_global_registry`, и точка
импорта реестра была одна на весь CLI; и содержит `fn main()`.

Внутри `main()`: `FuryCli::parse()` (clap разбирает `std::env::args`), затем
`commands::execute_command(args)`. Ошибка печатается в stderr строкой
`Fury CLI Error: {e}` и процесс завершается через `std::process::exit(1)`. Успех - обычный return из
main с кодом 0.

## Определение команд - src/cli.rs

Весь CLI описан derive-макросами clap, без ручного парсинга:

- `#[derive(ValueEnum, Clone, Debug, PartialEq)]` на enum'ах `LangFrom`
  (пока только `Python`) и `LangTo` (пока только `Ts`): ValueEnum даёт clap
  список допустимых значений для флагов, текст в `--help` и парсинг строки в
  вариант; `PartialEq` нужен обработчикам для сравнения, `Clone` - потому что
  clap отдаёт владение значениями;
- `#[derive(Parser, Debug)]` на структуре `FuryCli` с атрибутом `#[command(name
  = "fury", about = ..., propagate_version = true)]`: `name` должен совпадать
  с именем бинарника, иначе clap будет печатать другое имя в usage;
  `propagate_version` проставляет версию всем подкомандам;
- `#[derive(Subcommand, Debug)]` на enum `Commands` с единственным вариантом
  `Generate`.

Аргументы `Generate` и их семантика:

| Флаг              | Поле        | Тип                       | Смысл                                                                                                                 |
|-------------------|-------------|---------------------------|-----------------------------------------------------------------------------------------------------------------------|
| `-f, --lang-from` | `lang_from` | `Option<LangFrom>`        | язык источника; обязателен только когда `--src` - файл, но проверяет это не clap, а обработчик (см. разбор generate); |
| `-t, --lang-to`   | `lang_to`   | `LangTo`                  | целевой язык кодогенерации; обязателен всегда;                                                                        |
| `-s, --src`       | `src`       | `String`, default `"all"` | путь к исходнику с моделями или литерал `all` - «всё из глобального реестра»;                                         |
| `-d, --dst`       | `dst`       | `String`                  | директория назначения; создаётся, если нет.                                                                           |

`Option` у `lang_from`: если в src=all(значение по умолчанию), то это поле может быть пустым, так как
нам оно не важно - берутся все модели из реестра, это
проверяется в `handle_generate`. Enum'ы языков - точки расширения: новый
вариант = новый extractor или generator плюс ветка в диспетчерах.

## Ошибки - src/errors.rs

У CLI свой enum `CliError`, и `FuryError` ядра он не использует вовсе: классы
проблем здесь другие - файловая система, subprocess, разбор исходника.
`Clone` нет, в отличие от `FuryError`: ошибка CLI живёт до конца `main` и никуда
между потоками не ездит.

Варианты:

- `Io { path, source }` - любая файловая операция (чтение исходника, создание
  директории, запись файла). `#[source]` на `std::io::Error` сохраняет цепочку
  причин для отладки, а `path` в payload делает сообщение действенным: видно,
  какой именно путь не дался;
- `UnsupportedSourceLanguage(String)` - пользователь не указал `-f` там, где он
  обязателен, или указал язык, которого нет;
- `SchemaNotFoundInCore(String)` - имя модели найдено в исходнике, но схемы с
  таким именем нет в реестре; текст подсказывает «Did you register?»;
- `ParseError(String)` - всё, что связано с subprocess и разбором: не удалось
  запустить Python, импорт упал, интерпретатор не найден, моделей в файле нет.

## Extractors - src/extractors/

### mod.rs - диспетч и контракт

`extract_model_names(src_path, lang)` возвращает `Vec<String>` имён моделей из
файла. Контракт: пустой вектор - не ошибка здесь, ошибку «No models found»
поднимает вызывающий `handle_generate`. Для Python логика двухступенчатая:
сначала `python_import::import_python_module` (основной канал), и только если
он вернул пустой список - чтение файла и `python::extract_model_names`
(regex-fallback). Функция не валидирует язык сама: её вызывает диспетч после
match по `LangFrom`, поэтому ветка одна.

### python.rs - regex-fallback

`static PYTHON_MODEL_REGEX: LazyLock<Regex>` - регулярка компилируется один раз
при первом обращении: компиляция regex дорогая, а `static` без interior
laziness в Rust потребовал бы const-выражения, которого у `Regex::new` нет.
Паттерн: многострочный, ищет строку объявления класса, у которого в списке
базовых классов встречается слово `FuryBaseModel`, и захватывает имя класса
(группа 1).

`extract_model_names(content)` - просто `captures_iter` и сбор имён; никаких
проверок языка (гарантирует вызывающий).

> **Справка:** fallback уже, чем основной канал: регулярка матчит только
> `FuryBaseModel` в базах, а канал emit (см. ниже) видит любых наследников
> `BaseModel`. На практике это почти не стреляет, потому что fallback
> включается только при пустом emit, но знать об асимметрии стоит: класс
> `class User(BaseModel):` fallback не найдёт.

### python_import.rs - subprocess и канал emit

Главная идея: схемы моделей живут в аннотациях Python-классов, и единственный
способ их материализовать - дать интерпретатору выполнить модуль: сработает
`__init_subclass__` из fury-py, который зарегистрирует схемы в
`.fury_registry.bin` и (при установленной переменной окружения
`FURY_EMIT_MODELS`) напечатает в stdout строки `__FURY_MODEL__:{имя}`. CLI
ловит эти строки - это и есть канал emit, отделённый от пользовательских
`print` префиксом.

Шаги `import_python_module(src_path)`:

1. `parent_dir` - директория файла (`"models/user.py"` → `"models"`); пустая
   строка отфильтровывается и заменяется на `"."`, иначе `PYTHONPATH` получил
   бы дырку;
2. `module_name` - имя файла без расширения (`file_stem`); отсутствие имени -
   `ParseError("Invalid source file name")`;
3. `resolve_python()` - какой интерпретатор брать (порядок ниже);
4. сбор `PYTHONPATH`: сначала `parent_dir` (чтобы `import user` нашёлся), затем
   через разделитель (`;` на Windows, `:` иначе - `cfg!(windows)`)已有的
   значение переменной, если есть;
5. запуск `Command::new(python).arg("-c").arg("import {module_name}")` с
   `.env("PYTHONPATH", ...)` и `.env("FURY_EMIT_MODELS", "1")`, захват вывода
   через `.output()`; ошибка spawn - `ParseError` с текстом ошибки OS;
6. ненулевой код выхода - `ParseError`, в текст подмешан stderr subprocess'а:
   это единственный момент, когда пользователь видит traceback своего модуля;
7. разбор stdout: строки, начинающиеся с `__FURY_MODEL__:`, остальное
   отбрасывается.

`resolve_python()` - порядок источников интерпретатора и его логика:
`$FURY_PYTHON` (явный оверрайд для CI и экзотики) → `$VIRTUAL_ENV`
(`bin/python`, на Windows `Scripts/python.exe`; проверяется существование
файла - venv/uv-окружение самый частый кейс разработчика) → `$CONDA_PREFIX`
(аналогично, плюс `python.exe` в корне на Windows) → probe `python3` и `python`
из PATH через `--version` (берётся первый, который реально исполняется) →
`ParseError("No Python interpreter found")`. Probe через запуск, а не через
`which`, сознательно: наличие бинаря в PATH не гарантирует его работоспособность.

## Generators - src/generators/

### mod.rs - диспетч

`generate_all(schemas, dst_dir, lang)` - match по `LangTo`; единственная ветка
`Ts` уходит в `typescript::generate_all`. Точка расширения для новых целевых
языков: новый модуль рядом + ветка здесь, сигнатура для всех генераторов одна
и та же (`&[Arc<ModelSchema>], &Path`).

### typescript.rs - печать TS-классов

`generate_all(schemas, dst_dir)`: если директории нет - `create_dir_all`
(ошибка оборачивается в `CliError::Io` с путём); затем на каждую схему -
`generate_class_string` и запись в файл `{имя схемы в lower case}.ts`
(ошибка записи - тоже `Io` с полным путём файла). Lowercase в имени файла -
конвенция TS-модулей; коллизия двух схем, различающихся только регистром,
приведёт к перезаписи - никак не проверяется (подводный камень).

`ts_primitive_type(field_type) -> Option<&'static str>` - таблица
«FieldType → базовый TS-тип»: все числа (знаковые и без, float'ы) → `number`,
`Bool` → `boolean`, `String` → `string`, `Bytes` → `Uint8Array`,
`DateTime`/`Date` → `Date`. Для композитов (`List`/`Map`/`Object`) возвращает
`None`, и такие поля **молча пропускаются**: ни геттеров, ни TODO-шума. Дизайн:
кому нужны коллекции - пишет свои аксессоры поверх сырого `WasmRecord`
(`getObjectList`/`setObjectList` уже есть в fury-ts).

`wasm_methods(field_type) -> (getter, setter)` - пара имён метода границы WASM
для типа: `getBool/setBool`, `getString/setString`, `getBytes/setBytes`,
`getDate/setDate`, всё остальное (числа) - `getNumber/setNumber`. Эта пара -
единственное место, где тип поля влияет на имя вызова в сгенерированном коде.

`generate_class_string(schema) -> String`: сборка текста через `writeln!` в
`String::with_capacity(2048)`. `.unwrap()` на `writeln!` здесь легитимен и это
не лень: запись идёт в память (`String`), а не в IO, и вернуть ошибку она не
может по сигнатуре - падение невозможно, поэтому unwrap не скрывает риск.
Состав класса:

- два комментария-шапки: «AUTO-GENERATED BY FURY CLI. DO NOT EDIT.» и подсказка
  поправить путь импорта под свой билд wasm-bindgen;
- `import { WasmRecord } from '@fury/wasm-core';` - путь захардкожен константой,
  под неё предполагается alias в бандлере (или правка строки вручную);
- `export class {Name}` с приватным `readonly _internal: WasmRecord`;
- конструктор `constructor(buffer?: Uint8Array)` →
  `new WasmRecord('{Name}', buffer)`: оба режима fury-ts (парсинг байтов или
  пустая запись) доступны из коробки;
- на каждое примитивное поле: геттер с типом `base` или `base | null` для
  nullable (WasmRecord возвращает JS `null` для `FLAG_NONE`) и сеттер,
  принимающий **базовый** тип: запись null через сгенерированный сеттер
  невозможна (подводный камень);
  -_passthrough_ `toBytes(): Uint8Array`.

## Роутинг команд - src/commands/mod.rs

`execute_command(cli_app)` - match по `cli_app.command`; единственная ветка
распаковывает поля `Generate` и зовёт `generate::handle_generate`. Слой
существует отдельно от `main`, чтобы рост числа подкоманд не раздувал точку
входа и чтобы обработчики можно было тестировать напрямую.

## Разбор команды generate - src/commands/generate.rs (детали в конце)

`handle_generate(lang_from, lang_to, src, dst)` - весь end-to-end флоу. Ниже -
по шагам, с причинами именно такого порядка.

**Шаг 0. Выбор ветки источника.** `src.eq_ignore_ascii_case("all")` разделяет
два режима: дамп всего реестра или точечная генерация по файлу. Сравнение
case-insensitive, чтобы `ALL`/`All` не превращались в путь к файлу.

**Шаг 1a. Ветка `all`.** Берётся `get_global_registry()` и
`get_all_schemas()`. Важно: в этой ветке CLI ничего не импортирует и не
обновляет файл реестра - слепок `OnceLock` читает `.fury_registry.bin` из
текущей рабочей директории таким, каким его оставил последний процесс
(сервер, тесты, прошлый запуск CLI). Если файл пуст или отсутствует - реестр
пуст, и генерация молча ничего не напишет: ошибка не поднимается (подводный
камень: «успех» без файлов).

**Шаг 1b. Ветка файла.** Сначала `lang_from.ok_or_else(...)`: без языка
источника extractor не выбрать, поэтому `UnsupportedSourceLanguage` с текстом
«unspecified (required when --src is a file)». Затем
`extractors::extract_model_names`: subprocess-импорт обновляет
`.fury_registry.bin` и отдаёт имена через emit; при пустом emit срабатывает
regex-fallback. Пустой список имён - `ParseError("No models found in '{src}'")`.

**Шаг 2b. Чтение реестра ПОСЛЕ subprocess'а.** Только теперь вызывается
`get_global_registry()` - и это критичный порядок: `OnceLock` инициализируется
один раз на процесс и снимает слепок файла в момент первого вызова. Вызови мы
реестр до subprocess'а - в слепок не попали бы схемы из только что
импортированного модуля. Дальше на каждое имя - `registry.get(&name)`,
отсутствие - `SchemaNotFoundInCore` (имя есть в исходнике, схемы нет: модуль
не зарегистрировал класс, например он не наследник `BaseModel`).

**Шаг 3. Генерация.** `generators::generate_all(&schemas, &dst_path, lang_to)`:
создание директории, печать классов, запись файлов (см. раздел generators).

**Шаг 4. Копия реестра рядом с фронтендом.** Если `.fury_registry.bin`
существует в CWD, он копируется в `dst/.fury_registry.bin` - именно этот файл
фронтенд импортирует как ассет и передаёт в `loadRegistry`. Копирование
best-effort: `let _ = fs::copy(...)` - ошибка игнорируется сознательно
(генерация классов уже успешна, отсутствие блоба фронтенд обнаружит сам при
`loadRegistry`), но из-за этого пропажа блоба не видна в логах CLI (подводный
камень).

**Шаг 5.** `Ok(())` - `main` возвращает код 0.

Итоговый инвариант порядка: в файловой ветке subprocess (обновление файла)
всегда предшествует первому чтению реестра процессом; в ветке `all` freshness
файла - ответственность пользователя.

## Подводные камни

- Реестр читается и пишется относительно **текущей рабочей директории**:
  запуск CLI из другой папки увидит другой `.fury_registry.bin` или не увидит
  никакого. Запускать из корня проекта, где лежит файл.
- Ветка `--src all` при пустом реестре завершается успехом без единого файла -
  проверяй содержимое `dst` руками.
- Regex-fallback матчит только `FuryBaseModel` в базах класса, emit-канал -
  любых наследников `BaseModel`; асимметрия видна только при пустом emit.
- Копия реестра в `dst` best-effort (`let _ =`): отказ диска или прав не
  попадёт в вывод CLI.
- Имена файлов генерируются в lower case: схемы `User` и `user` дадут один
  файл, последний перезапишет первый.
- Путь импорта `@fury/wasm-core` в сгенерированном коде захардкожен: нужен
  alias в бандлере или ручная правка строки (подсказка-комментарий уже в
  шапке файла).
- Сеттеры nullable-полей принимают базовый тип, записать `null` из
  сгенерированного класса нельзя.
- Композитные поля (`List`/`Map`/`Object`) в классах отсутствуют молча.
- CLI линкует fury-core с фичей `db` (sqlx), хотя база не нужна: лишний вес
  сборки, лечится `default-features = false`.
- Subprocess наследует CWD CLI: `.fury_registry.bin` пишется импортёром туда
  же, откуда CLI его потом читает - это и делает канал согласованным.

## Примеры

```bash
# Дамп всего реестра (файл .fury_registry.bin должен быть свежим в CWD):
fury generate -t ts -d frontend/src/fury_models

# Точечно по файлу моделей (импорт обновит реестр сам):
fury generate -f python -t ts -s backend/models/user.py -d frontend/src/fury_models

# Явный интерпретатор (CI, несколько Python в системе):
FURY_PYTHON=/usr/bin/python3.14 fury generate -f python -t ts -s models.py -d out/
```

## Что можно добавить (на будущее)

1. `fury-core` в зависимостях с `default-features = false` - убрать sqlx из
   линковки CLI.
2. Ошибка вместо молчаливого успеха в ветке `all` при пустом реестре.
3. Конфигурируемый путь импорта `WasmRecord` (флаг или конфиг-файл) вместо
   захардкоженного `@fury/wasm-core`.
4. Новые целевые языки: ветка в `generators/mod.rs` + модуль-генератор.
5. Guard коллизий имён файлов (схемы, различающиеся только регистром).
6. Сеттеры nullable-полей с явным `null` (или отдельный метод `clearX`).
7. Предупреждение в stderr при неудаче копирования реестра вместо `let _ =`.
8. Watch-режим: перегенерация при изменении файла моделей (для dev-флоу
   фронтенда).
