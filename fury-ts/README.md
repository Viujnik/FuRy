# FuRy-ts workspace

## За что отвечает

`fury-ts` - это fury-core, скомпилированный в WebAssembly, плюс тонкая JS-дружественная
обёртка `WasmRecord` поверх него. Смысл простой: браузер получает **тот же самый
бинарный формат**, что пишет сервер, и в цепочке «сервер → браузер» не появляется
JSON вообще ни на одном шаге.

Из артефактов крейт производит `.wasm`-модуль и JS-глит (glue-код) от wasm-bindgen.
В дереве репозитория лежат две собранные цели: `pkg/` (target `web` - ES-модуль
для бандлера/браузера) и `pkg-node/` (target `nodejs` - для node-окружения,
тестов и SSR). Сборка: `wasm-pack build --target web` и
`wasm-pack build --target nodejs` соответственно.

В `Cargo.toml` две особенности:

- `crate-type = ["cdylib", "rlib"]`: `cdylib` - это и есть wasm-модуль для
  wasm-bindgen, а `rlib` оставлен, чтобы крейт можно было линковать как обычную
  rust-зависимость (тесты, node-биндинги);
- `fury-core = { path = "../fury-core", default-features = false }`: ядро
  берётся без фичи `db`, то есть без sqlx и tokio. Они не компилируются под
  `wasm32-unknown-unknown` (там нет ОС с сокетами), да и браузеру база не
  нужна - ему нужны только схемы и кодек.

Остальные зависимости - это инструменты границы: `wasm-bindgen` (мост JS↔Rust),
`js-sys` (JS-примитивы: `Date`, `Uint8Array`, `Array`, `Reflect`),
`console_error_panic_hook` (читабельные паники в консоли), `bincode`
(реестр схем приходит бинарным блоком), `chrono` (конвертации дат на границе).

## Точка входа - src/lib.rs

Экспортируются ровно две функции, и обе обязательны для корректного старта.

`init_panic_hook()` - по умолчанию rust-паника внутри wasm выглядит как
безликий trap («unreachable executed») без сообщения и стека: в консоли
браузера невозможно понять, что случилось. Эта функция ставит хук
`console_error_panic_hook::set_once()`, который печатает сообщение паники и
её происхождение в консоль браузера. `set_once` означает, что вызывать функцию
можно при каждом старте приложения - хук установится ровно один раз.

`loadRegistry(bytes)` - на wasm32 нет файловой системы, поэтому
`SchemaRegistry::new()` стартует с пустой картой: читать
`.fury_registry.bin` напрямую браузер не может. Реестр приезжает бинарным
блоком: `fury generate` копирует `.fury_registry.bin` рядом со
сгенерированными TS-классами, фронтенд импортирует его как ассет и передаёт
байты сюда. Внутри: `bincode::deserialize::<Vec<ModelSchema>>` и `register`
каждой схемы в глобальный реестр. Вызывать один раз при старте приложения,
**до** первого `new WasmRecord(...)` - конструктор ищет схему по имени и при
отсутствии вернёт ошибку с подсказкой «call loadRegistry() first».

## Запись. WasmRecord - src/record.rs

### Устройство и конструктор

`WasmRecord` - обёртка над `BinaryRecord` из ядра (единственное поле `inner`).
Вся логика сериализации живёт в core; задача обёртки - перейти границу JS:
превратить JS-типы в `ValueType` и обратно и перевести ошибки в `JsValue`
(wasm-bindgen не умеет пробрасывать в JS rust-исключения, только значение/строку).

Конструктор `new(schema_name, buffer?)` работает в двух режимах. С `buffer` -
разбор прилетевших байтов через `BinaryRecord::from_raw_bytes`: проверка
заголовка (размер, magic `'F'`, версия), обход TLV-записей, запоминание
координат известных полей, молчаливый пропуск неизвестных. Без `buffer` -
пустая запись для сборки с нуля (например, форма на клиенте). Схема берётся из
глобального реестра по имени; не найдена - ошибка с подсказкой про
`loadRegistry`.

### Приватные помощники: field_schema и decode

`field_schema(field_name)` - поиск поля в схеме по имени, ошибка при
отсутствии. `decode(field_name)` - `get_field_bytes` (zero-copy срез памяти
wasm) плюс `ValueType::from_bytes` по типу из схемы. Через `decode` идут все
геттеры, поэтому декодирование ленивое: поле разбирается в момент обращения, а
не вся запись целиком.

### Геттеры и сеттеры: переход границы JS

`getNumber` / `setNumber` - в JS один числовой тип: IEEE754 double (`f64`).
Поэтому все целые (Int8..UInt64) и float'ы проходят через `f64`. Цена: double
точно держит целые только до 2^53, значения Int64/UInt64 выше этого порога
теряют точность на геттере - это ограничение самого JS, а не обёртки (в коде
стоит комментарий). BigInt сознательно не используется: обычный `number`
удобнее для потребителя API.

`getString` / `setString` - единственное место, где zero-copy невозможен:
строки JS живут в UTF-16, память wasm - в UTF-8, wasm-bindgen транскодирует с
аллокацией. Неизбежная плата за границу.

`getBool` / `setBool` - тривиально: байт ↔ boolean.

`getDate` / `setDate` - в core `DateTime` хранится микросекундами от эпохи,
`Date` - днями от эпохи; JS `Date` живёт в миллисекундах от эпохи и знает про
часовые пояса. `setDate` берёт `get_time()` (мс) и конвертирует: для
`DateTime` - `from_timestamp_millis` + `naive_utc` (договор: работаем в UTC,
пояса - забота границы), для `Date` - `ms div_euclid 86_400_000` = дней от
эпохи. Геттер идёт обратно: `timestamp_millis` в `js_sys::Date`.
Саб-миллисекундные микросекунды на границе теряются - цена JS.

`getBytes` / `setBytes` - `Uint8Array`; копирование в память wasm и наружу.

`getObjectList(field, constructor)` - поле типа `List(Object)`: каждый элемент
списка - байтовый blob дочерней записи. Метод принимает JS-конструктор
(сгенерированный TS-класс) и на каждый элемент делает
`Reflect::construct(constructor, [Uint8Array])` - то есть создаёт дочернюю
модель из её байтов. Возвращает JS-`Array` готовых объектов.

`setObjectList(field, jsArray)` - обратная операция: у каждого JS-элемента
вызывается `.toBytes()` через `Reflect` (duck typing: подойдёт любой объект с
`toBytes()`, а у сгенерированных классов он есть), blob'ы собираются в
`List(Object)` и пишутся в поле.

`finish()` и `toBytes()` - `finish` финализирует запись (вписывает заголовок;
если были мутации - компакция), `toBytes` копирует память wasm в `Uint8Array`.
Копия неизбежна: JS не может владеть rust-срезом, `Uint8Array` - это всегда
копия (view на общую Memory - пункт «на будущее» ниже).

### Приватный set_field и авто-reopen

Все сеттеры идут через приватный `set_field`: если запись финализирована
(например, разобрана из сети), автоматически вызывается `reopen()`, затем
`set_field` ядра дописывает новое значение, а следующий `finish()` делает
компакцию - пересборку буфера без мёртвых байтов. Зачем прятать это внутрь:
JS-API не должен заставлять пользователя вручную управлять жизненным циклом
BUILDING/FINISHED/REOPENED - JS-программист просто зовёт сеттеры и `finish()`
перед `toBytes()`.

## Как выходит ускорить (почему это быстрее JSON)

Обычная цепочка: сервер сериализует строку в JSON-строку → HTTP → браузер
делает `JSON.parse` → граф JS-объектов: аллокация на строку, на каждое поле,
копии строк, парсинг чисел. Всё это сразу и на все поля, даже на те, которые
никто не будет читать.

Цепочка FuRy: сервер пишет строку в `BinaryRecord` (байты) → тело HTTP-ответа
как есть → браузер делает `new WasmRecord(name, bytes)`: один проход по байтам
для проверки заголовка и построения таблицы offsets, **без создания объектов**
→ геттеры декодируют одно поле по требованию.

Откуда берётся ускорение: (1) нет `JSON.parse`/`JSON.stringify` - самой
дорогой операции браузера в этой цепочке; (2) нет промежуточных объектов:
память не растёт на строку, пока поля не тронули; (3) декодирование поля -
O(размер поля), а не O(размер строки); (4) схема известна заранее из
реестр-блоба, в payload нет никакого согласования схемы. Мутации добавляют
свой кусок ускорения: сеттеры + компакция позволяют править запись локально и
отправлять обратно байтами, снова без JSON.

## Путь записи: сервер → браузер → обратно

1. Сервер: fury-py `fetch_one`/`fetch_all` → `BinaryRecord` → `as_bytes()` →
   тело HTTP-ответа.
2. Браузер: `fetch` → `arrayBuffer` → `Uint8Array`.
3. Один раз при старте: `loadRegistry(байты .fury_registry.bin)`.
4. `new WasmRecord('User', bytes)`: валидация заголовка (размер, magic,
   версия), обход записей, offsets известных полей, пропуск неизвестных.
5. Геттеры - ленивое декодирование; сеттеры - авто-reopen и дописывание;
   `finish()` - компакция; `toBytes()` - отправка обратно на сервер.

## Подводные камни

- `loadRegistry` обязана быть вызвана до первого `WasmRecord`, иначе ошибка
  «schema absent from registry - call loadRegistry() first».
- Int64/UInt64 выше 2^53 теряют точность в JS `number` - ограничение языка.
- Даты пересекают границу в миллисекундах: микросекунды теряются; часовые
  пояса - договорённость «работаем в UTC».
- Строки - единственное не-zero-copy место: транскод UTF-8 ↔ UTF-16 с
  аллокацией.
- Null в буфере (`FLAG_NONE`) приходит в JS как `null`; поле, которого нет в
  записи вообще, даёт ошибку геттера «was never set» - это разные ситуации.
- Без `init_panic_hook()` паника в wasm - нечитабельный trap без сообщения.

## Что можно добавить (на будущее)

- BigInt для Int64/UInt64 (или opt-in режим точных целых).
- `toBytes` без копии: view на общую wasm Memory (аккуратно с временами жизни).
- Аксессоры для `Map` (getMap/setMap) по аналогии с `getObjectList`.
- Пакетный разбор: фрейм со списком записей за один вызов для `fetch_all`.
- Конфигурируемый путь импорта `WasmRecord` в кодогенерации (сейчас
  подсказка-комментарий в сгенерированном коде).
